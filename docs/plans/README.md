# docs/plans の書き方（仕様）

機能ごとの「実装方針と進捗」を書くフォルダ。複数の AI エージェント・セッションが途中で交代しても、このファイルを読めば続きから作業できるようにする。

## ルール
1. **実装の前に** `docs/plans/<機能名>.md` を作り、作業ブランチに commit して push する（最初の push はこのファイルだけでよい）。
2. 以後は**小さく頻繁に** commit・push し、そのたびに「進捗」を書き足す。トークン切れで止まっても、最後の push までの状態が分かるようにする。
3. 着手前に `main` を pull し、マージ済み PR と他のブランチの plans を確認する（別のエージェントも同じリポジトリに push している）。
4. 1機能1ファイル。ファイル名は英小文字とハイフン（例: `town-houses.md`, `drive-camera-look.md`）。
5. 完了（PR マージ）後もファイルは消さない。「進捗」に `済: マージ（PR #番号）` を書いて残す。
6. 短く書く。コードの説明はファイルパスと関数名で示し、コードそのものは貼らない。

## テンプレート

```markdown
# <機能を一言で>（実装方針と進捗）

- ブランチ: `claude/<ブランチ名>`（mamamaki12/open-world）
- 依頼: <依頼者>「<依頼の要点>」
- PR: #<番号>（出したら書く）

## 方針
- <どのファイル・関数をどう変えるか>
- <守る決まり・触らない場所>
- <テスト・確認のしかた>

## 進捗
- 済: <終わったこと>
- 次: <次にやること（引き継いだ人が最初にやること）>
- 課題: <未解決の問題・迷っている点>
```

## 書き方のコツ
- 「次」は1〜3行。引き継いだエージェントがそのまま着手できる粒度にする。
- 方針を途中で変えたら「方針」を書き直し、理由を「課題」か「済」に一言残す。
- 未着手の項目は方針に「（未着手）」と付ける。
- 画面確認した場合は何を確認したかを「済」に一言書く。
